# Forkop subscription check on primary VM25 core

At the user's request, tested Rust X as the primary sing-box service on the
existing OpenWrt 25 VM, without a package/service state snapshot. No isolated
core process was used. APK metadata still identifies sing-box-x 1.0.3-r1;
this is a VM-local binary replacement, not a packaged installation.

The initial Forkop configuration exposed upstream XHTTP schema differences.
Local changes accept session_id_table/session_id_length aliases, numeric range
values, named session alphabets, zero max_connections with max_concurrency,
and the default uplink chunk size for zero. Original subscription parameters
were preserved. The full generated config passed validation and Forkop's
watchdog.ready marker appeared with Rust X running.

The selected subscription group contains 42 VLESS nodes: 39 TCP, two XHTTP,
one gRPC. A Clash HTTPS HEAD delay probe succeeded on all 42 in Rust X.
Before the switch, the same probe on Sing-Box X succeeded on 37, with five
timeouts. These delay results alone do not establish traffic compatibility.

A temporary loopback mixed inbound and route to the subscription selector
were added to the primary generated configuration. Sequentially selected all
42 members through Clash API and fetched https://example.com using the VM's
curl through SOCKS5:

- 39 TCP/REALITY nodes: HTTP 000, zero response bytes, curl exit 56,
  `ssl_read returned: (-0x0000)`.
- Both XHTTP nodes and the gRPC node: HTTP 200, 577 response bytes each.

The temporary inbound and route were removed and the primary service restarted.
Forkop readiness was confirmed afterward. Rust X remains the primary core.
Temporary probe scripts containing API authorization were removed. No
subscription URLs, UUIDs, server credentials or API secrets are in this report.

The cause of the TCP failure is not diagnosed. Similar Vision failures were
recorded before protocol trimming in Forkop's
`docs/tachyon-core-primary-vm25-2026-10-10.md`; that is context, not proof that
the current failure is independent of trimming. The test does not prove
browser-client compatibility, UDP traffic, or long-running stability.

This first candidate failed the user's condition for a push, so it was not
pushed. The follow-up below records the fix and successful repeat checks.

Tested binary: 11,022,288 bytes (10.51 MiB), SHA-256
`149d9c0eab2c0a036d93d273cdbf177f59a9aac68456d8bef8a98253e5a785fd`.
Earlier size comparisons in RUST-X.md apply to the earlier candidate before
these XHTTP compatibility fixes.

## Vision Direct fix and repeat checks

The same TCP/REALITY node succeeded with curl restricted to TLS 1.2 and failed
with curl's normal TLS 1.3 connection. The Vision implementation treated the
peer's CommandPaddingDirect as an ordinary end-of-padding frame while the outer
TLS reader kept decrypting. Vision Direct requires reading the subsequent peer
bytes from the raw transport, because they already belong to the destination's
TLS connection.

Added a read-side switch through the VLESS/ALPN wrappers to the native TLS
adapter. It drains any remaining decrypted bytes and buffered raw socket bytes
before reading the socket. Outgoing data keeps its existing outer TLS framing;
no write-side Direct optimization is claimed.

Initial TCP transfers succeeded after the fix, but a manual sing-box restart
collided with Forkop's process ownership guard and interrupted that test run.
Repeated through Forkop's native per-section mixed proxy instead:

- Enabled mixed_proxy_enabled with mixed_proxy_port 2081 on the VM's existing
  tachyon_probe section, applied using the normal Forkop restart.
- All 42 group members returned HTTP 200 and 577 response bytes from example.com
  through SOCKS5 with curl's default TLS version, including all 39 TCP/REALITY.
- A 1 MiB HTTPS download succeeded on a TCP/REALITY node, both XHTTP nodes and
  the gRPC node; all four returned HTTP 200 and exactly 1,048,576 bytes.
- Forkop readiness confirmed with the core remaining under procd.

Tested fixed binary: 11,025,232 bytes, SHA-256
`1a99198aadc9858a078c5e4880d7bdc8c3b3a44e6e2714e88ac77efc4a1ae568`.
These checks establish the tested HTTPS paths, not all UDP/TUN/VPN functionality
or long-running stability. The native mixed proxy was disabled after testing.

Source checks: all three Rust X config tests and all 13 existing Vision unit
tests passed; workspace formatting passed. Clippy on musl hit two existing
cast_possible_wrap warnings in core-crypto/afalg.rs (not changed by this work).
Standard Linux clippy also stopped on four existing TUN lints: two redundant
IP-address conversions and two packet-handler argument-count warnings. TUN
changes in this commit are formatting only; these lints remain unresolved.

## Follow-up: TUN / AF_ALG Clippy cleanup

AF_ALG now uses checked conversion for the libc I/O-vector count instead of
an unchecked cast. The same source supports libc fields with different integer
types; a local useless_conversion exception documents platforms where the
conversion is an identity. Redundant TUN IP-address conversions were removed.
The two packet handlers retain their explicit event-loop arguments with narrow,
documented too_many_arguments exceptions; packet-processing logic is unchanged.

Strict Clippy passed for core-runtime/core-config libraries with legacy-protocols
on both x86_64 GNU/Linux and musl. This is not a claim that every workspace target
or the reduced profile is warning-free. Existing reduced-profile dead-code build
warnings remain outside this cleanup. Existing tests passed: 12 TUN, 5 AF_ALG,
13 Vision, and 3 Rust X configuration tests.

The rebuilt reduced binary was installed as the primary VM25 core. All 42
subscription members again returned HTTP 200 and 577 bytes through the native
mixed proxy. The temporary mixed proxy was disabled after the check.
Binary SHA-256: `9b03d44ef5a6c46b4df577528a5d885218cc0157e3efae1665a4a9092972c28d`.
