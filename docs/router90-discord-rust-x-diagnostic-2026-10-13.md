Clash API /connections showed three UDP flows to the endpoint, all chains=[direct-out], with rule=inbound=[tproxy-in dns-in source-dns-in] => sniff(). The direct egress sockets were owned by the Rust X process (confirmed /proc PID fd ownership), with corresponding WAN-origin UDP conntrack entries to the voice server. Thus interception occurs but core routing falls through to route.final=direct-out.

Root cause in local Rust X source: crates/core-runtime/src/route/rule_set_index.rs parse_ranges() splits only on hyphen; crates/core-runtime/src/route/rule_set.rs port_range_contains() does the same. Colon ranges generated by Forkop are therefore silently unmatched. Ordinary route-rule parsing in rule.rs uses colon. Existing rule-set tests cover hyphen ranges, missing this generated configuration case.

Monitoring issue: route_walk_packet records each matching action, including nonterminal sniff. When no terminal route matches, the final direct outbound is returned while matched_rule still refers to sniff. This explains a misleading displayed rule; captured flow byte counters also read zero despite kernel packet evidence.

Suggested focused fix: support colon range syntax in both rule-set matching paths while retaining existing hyphen compatibility; test the actual Discord tuple with network/IP/port constraints and negative controls. Separately make fallback route metadata describe the final route. No binary A/B core switch or voice-quality retest performed in this diagnostic session.
