# Client outgoing Vision Direct

The client can initiate PaddingDirect after inspecting the inner ServerHello: TLS 1.3 supported_versions and cipher 0x1301 through 0x1304 qualify, matching Xray's set without CCM_8. TCP and handshake-record fragmentation are supported with bounded staging buffers released after detection. Malformed, oversized, unknown-version/cipher and HelloRetryRequest inputs conservatively retain outer TLS unless the peer independently confirms Direct. Only the TCP fingerprint TLS wrapper supports initiating raw writes. The final padded frame is fully written through outer TLS before raw writes begin; pending ciphertext prevents the switch. No server code or configuration changes are required. The outer REALITY/TLS handshake is unchanged.

The original peer-confirmed implementation passed 15 Vision tests, two TLS buffer/transition tests and three relay-buffer tests. The TLS test checks pending ciphertext refusal, original plaintext byte accounting and raw bytes after the switch. Standalone release CLI builds successfully. Full CI and ARM runtime verification were not performed locally.

Historical measurements of the peer-confirmed implementation (not new measurements of independent detection): local x86_64 OpenWrt 24/25 VMware comparison, 2026-10-16: four concurrent verified TLS1.3 HTTPS uploads over VLESS TCP REALITY Vision to Sing-Box X1.0.4; local HTTPS and local REALITY disguise target. Two trials per variant per VM in before/after/after/before order, 2 GiB per trial, 16 GiB total. Same release toolchain/profile, allocator, buffer sizes and one worker pinned to guest CPU0; no concurrent compilation. Throughput 999.73–999.85 Mbit/s without transfer errors.

This is a 47–49% relative process CPU reduction for this eligible upload workload, not a general protocol/download/ARM claim. Only two observations per variant; host physical-core affinity not fixed. RSS differences were small and do not establish a memory improvement. TLS1.2 fallback and simultaneous upload/download smoke checks passed on both VMs. No production package was replaced for these measurements.

A separate EOF investigation found outer TLS close_notify emitted by the reference REALITY server after switching to raw Direct when the inner HTTPS origin closes without close_notify. Its ciphertext authenticated with outer rather than inner TLS keys. The issue reproduces before this change and with a Sing-Box client. A correctly shutting-down rustls HTTPS origin passes strict EOF checks. This patch does not filter alerts or hide that server shutdown issue; no test traffic secrets or configurations are included here.

The peer-confirmed implementation did not initiate upload Direct in the observed Xray 26.7.28 sessions: clients sent PaddingEnd before the server sent Direct. Independent ServerHello qualification addresses that timing constraint. Verification results for the independent implementation are recorded separately.

Independent implementation verification (2026-10-16): 18 Vision tests, two TLS buffer/transition tests and three relay-buffer tests passed; x86_64 musl Rust X release CLI built. With the owner's unchanged Xray 26.7.28, each OpenWrt VM ran gstatic 204, Cloudflare 64 KiB download and 1 MiB upload with both clients (12 successful requests). Sanitized server debug intervals correlate three test sessions per variant/VM by destination and Python TLS ClientHello size. All six old-client sessions sent PaddingEnd; all six new-client sessions sent PaddingDirect before peer Direct. UUID does not appear in these debug lines, so attribution uses bounded intervals, destinations and ClientHello shape rather than an explicit user identifier. No server configuration/service changes were made.

A local rustls HTTPS origin with proper close_notify passed all 16 strict TLS 1.2/1.3 close tests (direct control and Vision, two repeats per VM). Installed package lists, Forkop service state and recorded configuration/binary hashes matched before and after temporary tests. ARM runtime and full CI remain untested; this is not a published package release.

Local throughput regression comparison against b96b1d9: unchanged Sing-Box X1.0.4 reference peer, four simultaneous verified TLS1.3 HTTPS uploads, 2 GiB/trial, old/new/new/old per VM (8 trials, 16 GiB), same release profile and worker affinity, no concurrent compilation. OpenWrt24 old CPU 41.90–42.48%, new 41.67–41.85% of one vCPU; all ~999.8 Mbit/s. OpenWrt25 new 41.09–41.67% at 999.74–999.87 Mbit/s; old matched-throughput trial 41.03% at 999.73 Mbit/s. The other old OpenWrt25 trial reached only 952.18 Mbit/s with 30.87% CPU. That trial does not establish an equal-throughput CPU comparison, and this small series does not support a precise percentage gain/regression. All transfers passed; no additional CPU saving is claimed for this peer, which already enabled Direct with b96b1d9. RSS differences do not establish a memory improvement. VM package/service/configuration state matched after cleanup.
